# Parametric assets and prefab viewer

## Purpose and status

All models and textures must be generated by Crust code. Asset authors must
work with dimensions, construction rules, and reusable operations. They must
not list vertices or assign individual texels for each asset.

This document specifies the content system. The first implemented slice is the
[radial start room](../../assets/rooms/radial-start.crs) and recipe viewer: profile lofting, caps,
surface regions, panel textures, collision output, and runtime dimension edits.
Keep room-specific design notes in the corresponding Crust file comments.
Do not create a separate Markdown document for each room.
The [engine gap register](engine-gaps.md) records the remaining engine work.

Keep the [game design](../../../SPINWARD.md), [rendering design](../render/rendering.md),
[room catalogue](room-catalogue.md), and [room connection contract](room-format.md).
The catalogue defines what rooms contain. This design defines how to build,
inspect, and reuse that content.

## Required result

A prefab recipe must produce these related outputs:

- A render mesh with surface regions and texture coordinates.
- Generated indexed textures and palette definitions.
- Collision geometry and stable surface identities for hook contacts.
- Connection sockets with local frames and opening dimensions.
- Clearance volumes, bounds, and named parts for inspection.

One parameter change must update all affected outputs. The game and viewer
must consume the same generated asset. No viewer-only version of a model is
permitted.

The source is Crust. Imported meshes, painted bitmap dependencies, and an
external modeling application are not part of the required build. Cached
outputs are permitted, but must be reproducible from the Crust recipe and
its inputs through a root Crust entry point.

## Implemented recipe workflow

| Component | Contract |
| --- | --- |
| Parameter metadata | Recipe-defined names, units, ranges, defaults, and steps; one source for command-line input and keyboard controls |
| Indexed hull | Owned vertex, polygon, and corner-index storage; shared polygon edges use shared vertex IDs |
| Regular profile | Side count and angular phase; positive radius supplied for each ring |
| Rhombicuboctahedral hull | Six square, twelve rectangular and eight triangular faces; independent cardinal and diagonal face dimensions; full cube symmetry |
| Rhombi corner inset | Enlarge the eight corner faces inward; keep cardinal and diagonal socket planes fixed; preserve closed planar faces |
| Radial vertex cut | Cut each vertex with a plane normal to its radius; preserve original face IDs and regions; add closed cut faces with shared edges |
| Truncated cube | Six regular octagonal faces and eight triangular corners; shared boundary vertices; positive half-extent |
| Ring loft | Aligned rings along +Y; increasing heights; outward polygon winding |
| Hex junction | Join active cardinal HEX-6M ports with a convex three-ring shell; collar separates adjacent openings; omitted branches become continuous walls |
| Bent tube | Closed quarter-turn tube with straight ends and continuous axial and perimeter UV coordinates |
| Pipe route planner | Select random destinations, take the shortest clear lane path for each destination, reserve rounded bend clearance, enforce the recipe bend-angle limit and minimum sink count, and use additional sinks after exit routes fail; retain the lane graph for inspection |
| Pipe waypoint graph | Join distinct exits through wall corridors and three-way joints; reject cycles and repeated exits across a connected network; emit closed pipes with rounded bends |
| Solid cylinder | Closed solid along +Y, with axial and continuous perimeter UV coordinates |
| Helical tube | Closed solid along +Y with planar end sections, integer turns, matching end profiles, and UV distance along the helix |
| Caps | Close both end profiles with convex polygons |
| Polygon inset | Insert a smaller concentric port with the same side count and phase; retain a solid ring around the opening |
| Convex face inset | Insert a regular port inside a convex face; keep boundary vertex IDs and surface coordinates |
| Bordered port | Add face-edge and opening-rim seams around a regular port in a convex face; retain the port face ID |
| Face sectors | Divide a convex face into equal edge runs around an interior point |
| Surface conversion | Triangulate convex polygons; preserve region IDs; derive planar UV coordinates at a fixed physical scale |
| Room bundle | Own the hull, render mesh, local solid-part geometry and placements, collision index, and spawn frame |
| Material masks | Reusable rectangle and border operations in metres |
| Concrete and cable surfaces | Cast-panel joints, formwork marks, aggregate, and ribbed cable sheaths at physical texture scales |
| Panel material | Repeated rectangular or hexagonal metal plates, tread, ribs, pipe coupling bands, or a closed two-leaf door with grain, recessed joints, fasteners, and full-bright indicators |
| Viewer session | Own the window and renderer; compile no game or expedition sources |

The loft operations consume valid construction data. The recipe checks public
parameter ranges and coupled constraints before construction. Ring counts and
side counts must fit the hull storage address range. A general loft is not
necessarily convex: a room recipe must use a convex radius/height sequence.

Polygons retain semantic region IDs. Triangles have inward winding and render
on both sides for exterior inspection. Collision uses the same triangles as
an interior shell. Hull containment supplies the interior half-spaces.

Room parts contain closed, outward-facing solid geometry in local coordinates.
Each placement selects a triangle range, a label, and a rigid pivot frame.
Several placements can share one geometry range. Part indices identify placements;
labels can repeat. The room build appends placed triangles after the shell and
creates one solid collider per placement. A separate collision-only placement
list can pair solid bars with cutout render faces. Both outputs must use the same
pattern and dimensions. Connected rooms keep these solid
colliders when they open the shell ports. Spawn checks include solid parts. A room can disable player spawning and supply
only a preview camera pose. Such rooms can be shallower than the player diameter.
Game and demo entry points reject these rooms as starting locations.
The viewer uses the spawn point when the room centre has no player clearance.
Parts can specify constant linear and angular velocity in room coordinates.
The pivot frame is the pose at time zero. The game and viewer compute each pose
from absolute time. The mesh, collision solid, and attached tether anchor use
that same pose. Zero velocities keep a part fixed. Retained meshes stay in GPU
storage; each frame updates only their instance poses. Room reloads restore the
source pose and apply the current clock.
In the viewer, `--animation-tick N` fixes both part motion and material animation
at the selected tick. The clock rate is `MATERIAL_ANIMATION_HZ`.

A room can also contain fixture lights with local positions, colours, and radii.
The viewer displays these lights. Level assembly copies them into the room graph;
the game submits them through portal anchors. These small fixture lights do not
cast shadows. A full-bright material and a light source are separate properties.
A fixture period of zero gives steady light. A nonzero period uses the shared
flash envelope. Room-local cosmetic spark emitters use that same clock and
material period. They compute positions directly from the tick and seed, so
pause and seek need no particle replay. Author their paths within the room.
The viewer uses the asset's inspection ambient and headlamp settings; these
settings do not change game lighting.

UV coordinates use metres in each polygon plane. Panel materials specify tile
size, texture density, and border width. Size changes repeat the tile without
changing its physical border width. Each material has a 256-entry palette.
Indices 248–255 are full-bright and do not emit light. The renderer supplies
lighting and screen-space dither.
Hexagonal plates use a rectangular repeat: width is three plate radii and
height is sqrt(3) plate radii. Texture dimensions round up at the requested
texel density. Sampling spans the exact repeat extent on each axis.
A recipe can align the surface origin and axes with a connection frame.
For different repeat widths and heights, scale each UV projection axis by
the room UV unit divided by that material repeat extent. This keeps physical
plate dimensions fixed and the same across all polygons around an opening.

Tunnel recipes can select `hex_tunnel_style(style)` with a style index from 0 to 5.
The styles share tile dimensions and texel density. The game uploads each style
once and assigns its material to the rooms in a corridor run. It does not create
a texture copy for each room. `PanelMaterial.marking` selects no marking (0),
paired strips (1), split bars (2), or inset studs (3). The marking mask adds
full-bright inserts and dark housings to the base metal texture.

Metal materials specify panel height, relief pitch, a stable grain seed, and
separate metal, accent, and indicator colours. Indices 0–223 form the metal
ramp. Indices 224–247 form the accent ramp. Grain has low contrast; panel
edges and relief supply the main surface cues. These cues are baked into the
texture. They do not supply reflections or change collision geometry.
The ribbed finish uses continuous folded strips. It has no crosswise panel
joints or fasteners. Strip direction follows the surface's U axis.
Quad UV frames start at the face centre. Their U axis follows the mean direction
of opposite edges, so tapered faces have a centred slope direction. UV distance
continues to use metres.

Generation, triangulation, palette generation, and collision-index construction
run only when the asset is built or rebuilt. Frame submission uses a retained
mesh range. A rebuild constructs a candidate before replacing the displayed
asset. Invalid parameters keep the previous asset and show an error in the
window title and terminal. GPU upload errors stop the viewer.

### Recipe interface

A selected `.crs` file defines these functions:

- `room_parameter_count()`: number of editable dimensions.
- `room_parameter(index)`: range, default, and step for one dimension.
- `room_parameter_name(index)`: immutable name for that dimension.
- `room_build(values, asset)`: build a fresh owned room bundle, or report an error.
- `room_material_count()`: number of surface materials.
- `room_material(region, values)`: panel material for a surface region and the
  selected recipe parameters. Texture width and height are independent physical
  dimensions. Sleeve textures use the selected portal-to-door clearance.
  Rivet radii and seam widths stay constant in metres.

Use `asset_name("name")` for a parameter name. Names must be unique. Source
strings remain valid for the life of the program. The recipe can use normal
Crust functions and records. The viewer does not select a built-in room by
number or interpret the recipe's source.

### Viewer controls

```sh
crust viewer.crs assets/rooms/radial-start.crs
crust viewer.crs assets/rooms/radial-start.crs --help
crust viewer.crs assets/rooms/radial-start.crs --set radius 16 --set taper 8
crust viewer.crs assets/rooms/radial-start.crs --view outside --capture build/radial.ppm
crust viewer.crs assets/rooms/radial-start.crs --view start --width 1280 --height 960 --capture build/start.ppm
```

The first argument is the recipe file. `--build-only` builds without opening a
window. `--capture` selects headless output. Captures default to one frame;
`--frames N` sets a different count. Source edits require the root command again.
Parameter edits rebuild the asset without recompiling source.

| Key | Action |
| --- | --- |
| Tab | Cycle interior, exterior, spawn, and free-flight views |
| F | Enter free flight from the current camera pose; press again for interior view |
| WASD | Move forward, left, back, and right in free flight |
| Q / E | Move down / up in the camera frame in free flight |
| Shift | Increase free-flight speed from 4 m/s to 16 m/s |
| Arrow keys | Change the interior look direction or exterior orbit |
| Left or right mouse drag | Look inside or orbit outside; stop automatic rotation |
| Mouse wheel | Change exterior orbit distance |
| W / S | Change exterior orbit distance |
| Space | Start or stop automatic rotation |
| `[` / `]` | Select a parameter; print its name |
| `-` / `+` or `=` | Change the selected parameter by one step |
| R | Restore the selected parameter's default |
| G | Toggle the waypoint graph; cyan shows candidate lanes, yellow shows selected routes; hide solid props in this view |
| Esc | Close the viewer |

The spawn view uses the recipe's exact frame. Interior and exterior views use
neutral inspection light. There is no room-specific camera code in the viewer.
Use `--view fly` to start free flight at the recipe's spawn frame. Mouse drag
turns the free-flight camera about its local axes. It can look past vertical.
Movement uses elapsed time and passes through geometry. Rebuilding the asset
keeps the camera position. Space and arrow keys do not change the flight camera.

Use `--waypoints on` to start in waypoint view or to capture the graph.
Recipes can retain their lane graphs for this view. Search buffers are released
after route selection. Recipes without a graph keep their normal view.

The viewer draws each port's local ID and compatibility name on its closure,
with an outline of the actual hull polygon. Labels are readable from either
side and use depth testing. They are viewer geometry, not collision surfaces.
The font atlas is generated from the shared bitmap font in Crust. Label names
must use ASCII. Unlinked ports stay closed; an outline does not create a link.

Room bundles own a variable-size list of ports. Each port records its local ID,
shared profile, hull face ID, and rigid frame. The hexagonal inset operation
partitions a rectangular wall into a closure and eight convex surround faces.
It preserves shared outer edges and the wall's texture frame. The shared
profile supplies the opening vertices and allowed rotations. Names determine
compatibility; no polygon comparison selects a connection.


### Focused checks

```sh
crust tests.crs assets
crust tests.crs asset-viewer
crust tests.crs collision
```

The asset checks build the production recipe at its default, minimum, and
maximum dimensions. They check closed shared edges, convexity, planar faces,
spawn clearance, physical UV scale, and player/hook sphere contacts against every polygon. They
also reject out-of-range parameters. The small room checks
contacts on internal triangle diagonals. A rounding margin on shared coplanar
edges prevents both adjacent faces from rejecting the same seam contact.
Boundary edges retain their geometric tests.

The focused viewer check changes the radius through the production rebuild
path. It checks rejected-edit recovery, retained mesh replacement, and visible
pixels after the final upload. It does not run the expedition.

Inspect interior, exterior, and spawn captures before adding detail. This proof
covers a generated room, its closed named ports, and collision data. Connected rooms and
gameplay transfer require the checks in the room-format document.

## Authoring layers

| Layer | Responsibility | Example |
| --- | --- | --- |
| Style rules | Shared proportions, dimensions, surface roles, and detail scale | Pipe sizes, flange thickness, rib pitch, indicator colours |
| Modeling operations | Construct shapes and preserve named regions | Profile, extrusion, sweep, revolve, inset, repeat |
| Material operations | Construct masks and combine surface layers | Panel border, repeated vents, warning strip, paint variation |
| Component recipe | Build one functional part from constrained parameters | Flanged elbow, support bracket, lamp housing |
| Prefab recipe | Arrange parts around routes and connections | Service corner, bulkhead, pump bay |
| Instance | Select a recipe, parameters, pose, and bounded variation | A particular bulkhead in an expedition |

Keep these responsibilities separate from mission logic, input, and rendering.
Use ordinary Crust functions and parameter records first. A graph editor or a
new interpreted asset language is not required. Add a Crust language feature
only when a concrete authoring or ownership case requires it.

## Shared style and parameters

Hex junctions have one material region per entrance, in port order. The wall,
floor, and ceiling patches at an entrance use that region. Each patch starts
its axial texture at the port plane and uses the tunnel's cross-section phase.
A level can assign a different material to each region. The junction recipes
expose `style-entry`, `style-east`, `style-exit`, and `style-west` for their ports.
Different entrance styles have narrow dark seams along their shared surface
boundaries. The seams use the material border width.

Expose a small set of independent dimensions. Derive related dimensions from
shared tables and construction rules. A nominal pipe size determines its
compatible flange, support, and socket sizes. Increasing a cabinet width
must preserve its panel border and select a valid vent arrangement.

Specify units, accepted ranges, defaults, and relationships for each public
parameter. Include discrete options for construction variants. The same
parameter description must supply viewer controls and input validation.

Style rules must define:

- Preferred structural dimensions and spacing.
- Wall thickness, chamfer size, and bend-radius relationships.
- Facet counts and detail choices appropriate to the projected shape.
- Material roles and physical texture density.
- Indicator and warning placement at functional features.

Keep large forms, supports, and small surface details distinct. Concentrate
small details at connections, access panels, and controls. Do not distribute
bolts or noise over every surface. A room needs a dominant structure, a clear
route, repeated structural spacing, and an identifiable return view.

Use authored configurations before random variation. A seed can change wear
or select an approved panel variant. It must not decide socket compatibility,
minimum clearance, or the basic function of the room. Give parts stable seed
keys so that adding one part does not change every other part.

## Geometry operations

Start with the following operations, implemented only as the first assembly
requires them:

| Operation | Required behaviour |
| --- | --- |
| Profile | Define a closed section from dimensions, lines, and controlled arcs |
| Extrude | Extend a profile; identify side, start, and end regions |
| Sweep | Follow a path with explicit section orientation and bend rules |
| Revolve | Rotate a profile around an axis with controlled facet count |
| Inset and recess | Create panel borders and cavities within supported profiles |
| Transform and mirror | Preserve surface roles, socket frames, and winding |
| Repeat | Fit parts to a span or angle; retain margins and end conditions |
| Assemble | Place components through local frames or compatible sockets |

Put chamfers into profiles where possible. Do not require a general mesh
bevel or Boolean kernel to build a flange or recessed frame. General Boolean
operations need robust intersection and topology rules before use. SDF mesh
generation needs a separate proof for surface extraction, material mapping,
and collision. Neither is the initial geometry foundation.

Operations must return semantic regions such as `outer_rim`, `housing`,
`recess`, `mount`, and `indicator`. Later operations select these regions,
not numeric vertex or face indices. Change facet count without changing the
meaning of a material assignment or connection.

A sweep must define its frame at bends and its treatment of tight radii.
Reject self-intersection and invalid dimensions at the authoring boundary.
Triangulation must preserve openings, winding, and region boundaries.

Keep the editable construction data separate from packed render data.
Generate bounds and collision acceleration data when the asset is built.
Do not repeat topology operations in a frame or collision query.

## Texture and material operations

Use reusable two-dimensional operations: rectangles, circles, polygons,
lines, distance masks, transforms, repetition, outlines, insets, gradients,
layer composition, and bounded seeded variation. A library operation may
sample pixels. An asset recipe must describe features instead of pixel tests.

Build named recipes for painted panels, recessed vents, structural trims,
flanges, warning bands, and indicators. Supply each recipe with the surface
region's dimensions and local coordinates.

Geometry and material recipes must share their feature layout. One flange
layout positions both visible fasteners and their surface marks. A panel
layout positions both its recess and painted border. Do not calculate these
positions independently.

Generate trim sheets for repeated structural strips. Generate separate texture
regions for device faces that need a distinct layout. Choose resolution from
physical texture density and the intended viewing distance. Increasing an
asset dimension must not stretch a border or enlarge individual texels.
Texture descriptors must supply dimensions, storage range, and addressing
rules. Atlas regions need border rules that prevent sampling adjacent parts.

Keep texture identity separate from palette and light response. Several
textures can use the same palette. Palette size must be explicit; four source
colours per material is not the target contract. Do not require a final-frame
palette reduction.

Generate full-bright classification with the source colours. Full-bright
texels remain visible in darkness but do not create lights. Preserve the
current 16 by 16 screen-space light interpolation and dithering at render
time. Do not bake that screen-space pattern into asset textures.

Start with host-side Crust generation. Move a measured expensive operation to
Crust compute code only when it improves the asset build. Vulkan compute
remains the rendering path in either case.

## Collision and connections

Generate render and collision data from the same construction description.
They need not have the same tessellation. Small painted details need no
collision. A visible opening, ledge, flange, or hook surface must have a
matching contact boundary at gameplay scale.

For the first assembly, generate a static triangle collision surface with a
spatial index. Reuse the construction topology for its edges and adjacency.
Keep the spherical drone and hook. Use continuous sphere sweeps against faces,
edges, and vertices, with a defined initial-overlap policy. Internal edges on
a coplanar surface must not become false ridges. Add other collision primitives
only when they improve a measured case or express required moving geometry.

Contacts must identify the instance and surface, not only time and normal.
A hook attachment must retain the local contact point and its owning instance.
This supports inspection and is required before moving anchors can work.

Room sockets follow the [room format](room-format.md). Each has a unique local
port ID, compatibility name, local rigid frame, and allowed rotation count.
Names determine compatibility without polygon matching. The shared profile
supplies the opening recipe and clearance. Both sides must meet without a gap
in drawing or collision. Closed sockets must have a generated closure.
Changing dimensions must update that closure and use a compatible profile name.

Each room has a convex hull and its own local space. Props use that space.
Build non-convex room variants from several connected convex rooms.

Rigid instance placement must transform mesh, collision, sockets, and bounds
together. Non-uniform size changes belong in recipe parameters, where wall
thickness and clearances can be checked. Do not hide a bad fit with a position
clamp or invisible collider.

Ordinary room connections and transformed gameplay portals are distinct.
Both need compatible openings. A transformed portal also needs a source and
destination space and state-transfer rules. Preserve that game feature; the
current expedition's ordinary doors do not implement it.

## Generated asset ownership and runtime cost

The build returns one owned asset bundle with immutable meshes, texture data,
collision data, sockets, and bounds. Instances hold asset references and poses.
Runtime door leaves use separate solid parts in `RoomAsset.door_leaves`.
Each leaf supplies its opening translation in room coordinates. The asset also
supplies the regular-polygon aperture for the prediction trigger. Leaf storage
grows during construction; the runtime has no fixed leaf-count limit.
The viewer draws their closed pose. Room assembly keeps them out of the static
room mesh and assigns each leaf a retained mesh range and collider identity.
The game changes their poses with a bounded translation schedule. See
[moving mesh contacts](../collision/kinematic-meshes.md#controlled-translation).

The renderer consumes geometry and material data without knowing recipe names,
biomes, missions, or viewer controls.

Classify work as follows:

- Asset build and rebuild: cold path. Allocation, triangulation, texture
  generation, validation, and spatial-index construction are permitted here.
- Rendering and collision queries: hot paths. Consume built data; do not
  execute recipes or allocate per primitive.
- Capture and topology checks: test paths. They use production asset output.
- Replacement and shutdown: ownership paths. Retire CPU and GPU resources only
  after all users have completed.

Validate external parameter files and viewer input once. Reject non-finite
values, unsupported configurations, and failed allocations with diagnostics.
A validated asset is trusted by internal consumers. Internal invariant
failures must not appear as a successful partial asset.

A generated cache key must include recipe identity and revision, parameters,
seed, style revision, generator revision, and output format. Define stable
ordering and hashing. Cache data is replaceable output, never the sole asset
source. Do not promise byte-identical floating-point output across backends
until that property has been tested.

## Standalone prefab viewer

Use `crust viewer.crs ROOM.crs` as the separate root entry point. The room is a
normal Crust source file, compiled with the shared asset library. The root must
bootstrap and build through the same Crust root mechanism as the game. Reuse
the SDL window, Vulkan renderer, capture path, and asset library. Keep viewer
input and state separate from game missions and simulation progression.

Use `--portals open` to hide connection face closures during inspection. Shell
walls, solid parts, and port labels remain visible. The default is `--portals closed`.
This option changes the preview mesh only; collision and connection data stay intact.

The first viewer must provide:

- Asset and named configuration selection.
- Typed parameter controls with ranges, units, and reset-to-default actions.
- Orbit, pan, zoom, and free-flight cameras with a scale reference.
- Neutral light, production game light, and dark headlamp-only views.
- Silhouette, wireframe, surface-role, UV, and texture views.
- Full-bright mask, collision, socket, and clearance overlays.
- Isolation of named construction parts.
- Geometry count, texture memory, build time, and render timing.
- Fixed-camera captures and configuration comparison sheets.

Parameter changes regenerate the asset without compiling source. Source edits
require a Crust rebuild. Provide an explicit rebuild/reload action first;
a file watcher can call the same action. Preserve camera, parameters, and
inspection mode across a successful reload.

Build the replacement before switching assets. A failed build must show its
error. If the old asset remains visible, label it as the previous successful
build. Do not show it as the requested result. Stop dependent collision tests
until the requested build succeeds. Do not require live library unloading or
an ABI-stable plugin system for this workflow.

Expose a headless capture mode using the same asset selection and parameters.
Store comparison inputs with the recipe. A screenshot alone is not enough to
reproduce a result.

## First production proof

Start with the [closed radial room](../../assets/rooms/radial-start.crs). Prove its parametric hull,
materials, local spawn, and collision output in the standalone viewer. This is
the first asset selected for implementation. Its prism faces have named hexagonal
ports with closed unused openings. Room links are a separate assembly step.

Before a room-wide component library, extend that proof to a connected assembly:

- A profiled opening with a recessed frame.
- A pipe elbow, flange pair, and attached support bracket.
- One indicator region and a coherent generated panel/trim material.
- Two connected room stubs with a sealed, traversable opening.

Supply at least three distinct size configurations. Sweep the accepted
parameter endpoints and coupled extremes, including pipe size versus bend
radius and opening width versus frame thickness. Use fixed seeds for checks.

The same generated asset must appear in the viewer and a playable expedition.
The drone and launched hook must interact with its actual collision data.
This is the required test across the ownership boundary from recipe output
to the final rendered and playable result.

Before changes, capture the current room and measure its build, upload,
render, simulation, and prediction costs on named hardware. Then measure the
new assembly at the same resolution and camera positions. Record asset size,
visible instance count, submitted and clipped triangles, tile candidates,
texture bytes, collision candidates, and contacts.

Proposed acceptance targets, not measured results:

- Parameter rebuild reaches the displayed result within 100 ms for this
  assembly; report build and upload time separately.
- The integrated scene sustains a 60 Hz frame budget at 960 by 540 on the
  selected baseline GPU. Record GPU time and end-to-end time separately.
- Simulation completes within its 120 Hz tick budget with the assembly
  installed. Measure prediction work separately from the active tick.
- No opening leaks, false collision ridges, missed high-speed contacts,
  invalid topology, silent capacity truncation, or texture-region bleed.
- Proportions, border widths, texture density, and socket fit remain correct
  across the accepted parameter range without per-variant vertex or texel edits.
- Human inspection accepts the silhouette, construction, and dark-state
  readability in entry, close, and return views. Passing tests is not art approval.

Test AMD and Intel rendering through the available hardware. Run the same
suite on NVIDIA before claiming three-vendor validation. Record the actual
hardware and driver with each result.

If this proof fails, fix its measured cause before adding another generator
family. Do not reduce the asset to boxes merely to preserve prototype limits.
Do not expand into a general editor before the viewer-to-game proof passes.

## Delivery order

1. Establish the baseline and the assembly's parameter and socket contract.
2. Add the minimum mesh, material, and collision output needed by that assembly.
   Fix the blocking renderer and collision limits listed in the gap register.
3. Add the standalone viewer and prove parameter regeneration and inspection.
4. Install the exact output in the game. Pass the rendering, contact, clearance,
   ownership, and cost gates above. Obtain visual approval.
5. Extract additional component recipes from accepted content. Apply them to
   the room catalogue. Prove room composition and instance scaling separately.

The broader world and physics gaps have explicit triggers in the register.
They must be resolved before content uses those capabilities. Static asset
work does not authorize a moving-machine or multi-drum implementation by itself.

### Moving lightning contacts

A room can define `ArcEmitter` records in `RoomAsset.arcs`. Each emitter has a
reference contact, a rotation pivot, an angular velocity, and a ray direction.
The cycle-start tick sets the contact pose. Both contacts stay fixed for that
cycle. A shared cycle seed synchronizes emitters with different bolt shapes.
A static collision-tree query sets the other contact on the nearest surface in that room. An unloaded room emits no
strike. Geometry loading remains under room admission control.

The seed selects active cycles and the bolt path. Bolts appear at full intensity
and fade with their contact sparks and midpoint light. The near-black tail is
transparent. Both materials use the emitter period. Submit the effect surfaces before retained mesh instances.
The game propagates the light through portal anchors. Effect surfaces have no
collision and cast no shadows.

### Room-local attraction

`RoomAsset.attraction` defines an optional axial field. Level assembly copies the
field into the room graph and collision scene. Scene snapshots retain the field
for prediction. Changes to global room placement preserve its local coordinates.

Player motion, flying hooks, and trajectory prediction use the same field. The
pull has no axial component. Its magnitude falls with inverse distance outside
the core radius and falls linearly to zero inside that radius. A disabled field
adds no acceleration. The field is independent of drum spin and remains local
to its room across portals.

Powered conduit recipes enable this field. See
[the conduit recipe](../../src/assets/prefabs/conduit-tube.crs) for the strength
and [the flight environment](../../src/game/flight/environment.crs) for the force
law. Orbiting debris keeps its authored motion.
